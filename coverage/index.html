Reverse-engineered, read-only

How the Hotspawn list is read

Reconciliation record ↓
A

Authoritative fixture array

The same public scheduled-fixture API that feeds Hotspawn’s own client is the inventory of record. Every CS2 record in it is kept — upcoming, past-start and unknown-schedule alike — so newly listed matches appear on the next successful refresh.

Original fixture API
B

Two rendered pages cross-check it

Both public lobby pages embed the fixture list in an Angular hydration block (ng-state). The collector reads that block from each page and requires the same unpaginated ID set as the API. A readable page that disagrees fails the refresh closed; when no page can be read the API array is published with an explicit “unavailable” cross-check marker instead of a reconciliation claim. A cache-busting query string requests a fresh server render because the CDN can serve stale HTML.

Official lobby Official CS2 lobby
C

Fail-closed contract

Duplicate IDs, an empty array or a changed schema invalidates the refresh — it is never accepted as an empty or partial feed. Picks lock 5 minutes before each fixture’s scheduled start per Hotspawn’s own rules page; per-fixture lock timestamps take precedence on this dashboard.

Hotspawn lock rules for manual review
D

4–8 hour freshness bound

Primary refresh slots run every four hours with catch-up slots 2.5 hours later, so one dropped run still leaves data inside the eight-hour bound. After eight hours without a successful observation the site warns against treating the snapshot as current, and original timestamps are never restamped.
